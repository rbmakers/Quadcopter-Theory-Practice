Betaflight 調度器深度分析

單棧協作式調度器 · 雙域分離 · 動態優先級准入控制

一、架構定性：確定性協作式調度器

Betaflight 的 scheduler() 並非 RTOS，也不是單純的 while(true) 加中斷。它是一個單堆疊、零上下文切換、時間觸發與事件觸發混合的專用調度器。所有任務都是透過函式指標直接呼叫，沒有任務控制塊 (TCB)、沒有堆疊切換、沒有 PendSV 異常。

這意味著：

  • 任務切換成本 ≈ 函式呼叫成本（數個 CPU 週期），而非 RTOS 的數十至數百週期。
  • 無優先級反轉、無死鎖（因為不存在搶佔，也不存在互斥鎖）。
  • 記憶體佔用極小（無需為每個任務配置私有堆疊）。

二、雙域調度：實時域與非實時域的分離

2.1 實時域 (Real-time Domain)

由 TASK_GYRO、TASK_FILTER、TASK_PID 組成嚴格順序鏈，對應 TASK_PRIORITY_REALTIME。

同步機制並非中斷觸發，而是輪詢鎖相：

// 計算下一個理論上應該執行 Gyro 的時間點 nextTargetCycles = lastTargetCycles + desiredPeriodCycles; schedLoopRemainingCycles = cmpTimeCycles(nextTargetCycles, nowCycles); // 當接近時間邊界時，主動輪詢等待（busy-wait） while (schedLoopRemainingCycles > 0) { nowCycles = getCycleCounter(); schedLoopRemainingCycles = cmpTimeCycles(nextTargetCycles, nowCycles); } // 精確到達時間點後，立即執行實時鏈 schedulerExecuteTask(gyroTask, currentTimeUs); if (gyroFilterReady()) schedulerExecuteTask(getTask(TASK_FILTER), currentTimeUs); if (pidLoopReady()) schedulerExecuteTask(getTask(TASK_PID), currentTimeUs);

這裡的 while 輪詢是刻意設計的。它捨棄了「中斷來了才執行」的傳統思路，改為主動追蹤 CPU 週期計數器，在精確的週期邊界上執行控制迴路。這消除了中斷延遲抖動（Interrupt Latency Jitter），達到次微秒級的時序精度。

Gyro 鎖相 (Phase-Lock)：

// 追蹤實際 EXTI 中斷時刻，消除累積偏移 int32_t gyroSkew = cmpTimeCycles(nextTargetCycles, gyro->gyroSyncEXTI) % desiredPeriodCycles; accGyroSkew += gyroSkew; // 每 GYRO_LOCK_COUNT 個週期校正一次 lastTargetCycles -= (accGyroSkew / GYRO_LOCK_COUNT);

調度器會持續比較「預期的執行時刻」與「實際的陀螺儀 EXTI 中斷時刻」，並透過移動 lastTargetCycles 來消除長期漂移。這類似於數位通訊中的 PLL（鎖相環）概念。

2.2 非實時域 (Non-realtime Domain)

實時鏈執行完畢後，剩餘的時間才用於執行其他任務（如 Serial、OSD、Battery、Baro 等）。這些任務的排程遵循三個原則：

  1. 動態優先級與任務老化：等待越久的任務優先級越高。
  2. 准入控制：只有預估能在下一個 Gyro 週期前完成的任務才被執行。
  3. 自適應保護邊距：根據歷史執行表現動態調整安全緩衝。

三、非實時域的三大排程機制

3.1 動態優先級與任務老化 (Task Aging)

靜態優先級僅決定初始權重，真正影響排程的是動態優先級：

// 時間驅動任務 task->taskAgePeriods = cmpTimeUs(currentTimeUs, task->lastExecutedAtUs) / task->attribute->desiredPeriodUs; task->dynamicPriority = 1 + task->attribute->staticPriority * task->taskAgePeriods;

taskAgePeriods 表示「這個任務已經欠了多少個週期沒執行」。等待越久，動態優先級線性增長，最終會壓過其他任務。

對於事件驅動任務（如 TASK_RX、TASK_OSD），則透過 checkFunc 觸發：

if (task->attribute->checkFunc(currentTimeUs, deltaTime)) { task->dynamicPriority = 1 + task->attribute->staticPriority; }

老化加速 (Expedite) 機制：

當任務長期無法獲得執行機會（taskAgePeriods > TASK_AGE_EXPEDITE_COUNT），調度器會強制降低其預估執行時間：

selectedTask->anticipatedExecutionTime *= TASK_AGE_EXPEDITE_SCALE;

這使得該任務更容易通過「時間預算檢查」，確保不會餓死 (Starvation)。

3.2 准入控制：以執行時間預估為門檻

這是 Betaflight 調度器最獨特之處。它並非單純選擇優先級最高的任務，而是檢查該任務是否能在下一個 Gyro 週期前完成：

timeDelta_t taskRequiredTimeUs = task->anticipatedExecutionTime >> TASK_EXEC_TIME_SHIFT; int32_t taskRequiredTimeCycles = (int32_t)clockMicrosToCycles((uint32_t)taskRequiredTimeUs); taskRequiredTimeCycles += checkCycles + taskGuardCycles; if (taskRequiredTimeCycles < schedLoopRemainingCycles) { // 時間夠，可以執行 }

anticipatedExecutionTime 是每個任務的自我估計執行時間，會根據歷史執行時間緩慢衰減更新：

if (taskExecutionEstimateUs > (selectedTask->anticipatedExecutionTime >> TASK_EXEC_TIME_SHIFT)) { selectedTask->anticipatedExecutionTime = taskExecutionEstimateUs << TASK_EXEC_TIME_SHIFT; } else if (selectedTask->anticipatedExecutionTime > 1) { selectedTask->anticipatedExecutionTime--; // 緩慢衰減 }

這是一種軟體層的 Worst-Case Execution Time (WCET) 估計，用來保證實時域不會被非實時任務侵蝕。

3.3 自適應保護邊距 (Adaptive Guard Margin)

taskGuardCycles 是一個動態調整的安全緩衝，機制類似 TCP 擁塞控制的 AIMD（加性增乘性減）：

if (cyclesOverdue > 0) { // 任務實際執行超過預估 + guard，增加邊距 taskGuardCycles += taskGuardDeltaUpCycles; } else if (-cyclesOverdue < taskGuardMinCycles) { // 任務提前完成且餘裕充足，減少邊距 taskGuardCycles -= taskGuardDeltaDownCycles; }

這確保了在負載變化（例如連接 Configurator 導致 Serial 任務變長）時，調度器能自動保守化，避免錯過 Gyro 週期。

當 taskAgePeriods > TASK_AGE_EXPEDITE_COUNT (預設 1)：

anticipatedExecutionTime *= TASK_AGE_EXPEDITE_SCALE

強制降低預估執行時間，使任務更容易通過「時間預算」檢查而被排程。

七、准入控制 (Admission Control) 邏輯

Betaflight 的創新之處在於以 執行時間估計 作為任務准入的條件，而非單純優先級搶佔：

准入條件

taskRequiredTimeCycles + taskGuardCycles < schedLoopRemainingCycles

或

scheduleCount & SCHED_TASK_DEFER_MASK == 0

（定期強制檢查）

或

taskId == TASK_SERIAL

（SERIAL 任務豁免時間預算檢查）

自適應保護邊距

taskGuardCycles：動態調整的執行時間緩衝。

• 若任務實際執行超過預估 + guard → guard 增加
• 若任務提前完成且餘裕充足 → guard 減少

類似 TCP 擁塞控制的加性增乘性減 (AIMD) 機制，確保不錯過 Gyro 週期。

九、Betaflight 調度器的核心設計創新

1. 雙域分離 (Dual-Domain Separation)

將任務明確劃分為 Real-time Domain (Gyro/Filter/PID) 與 Non-realtime Domain (其他所有任務)。實時域與硬體 EXTI 鎖相，非實時域在剩餘時間內動態填充，兩者互不干擾。

2. 執行時間估計排程

不同於傳統優先級搶佔，Betaflight 使用 anticipatedExecutionTime 進行准入控制。任務只有在其「宣稱」的執行時間加上 guard margin 能夠在下一個 Gyro 週期前完成時，才會被排程。

3. 輪詢硬同步 (Busy-wait Synchronization)

透過 while(schedLoopRemainingCycles > 0) 主動輪詢 CPU 週期計數器，而非依賴中斷觸發。這消除了中斷延遲抖動，達到次微秒級的時序精度。

4. 自適應參數調整

schedLoopStartCycles 與 taskGuardCycles 會根據實際執行表現自動增減，類似網路擁塞控制。這使調度器能在不同硬體負載下自我調節，維持穩定性。

十、設計哲學總結

Betaflight 的調度器體現了嵌入式系統設計中的「專用化優於通用化」哲學：

  1. 捨棄通用性：不實現完整的 RTOS 功能（沒有任務創建/刪除、沒有阻塞/喚醒、沒有 IPC），只保留飛控所需的「週期觸發 + 優先級調度」。
  2. 以空間換時間：用輪詢等待（消耗 CPU 週期）換取確定性時序，而非依賴中斷的「事件驅動」模型。
  3. 自我調節：透過 taskGuardCycles、schedLoopStartCycles、anticipatedExecutionTime 等參數的自適應調整，使調度器能在不同硬體負載與飛行狀態下自我穩定。
總結：Betaflight 的調度器是一種針對飛行控制優化的確定性協作式排程器，它捨棄了 RTOS 的通用性與傳統中斷的靈活性，換取了極致的時序確定性與零上下文切換開銷，這正是高頻 PID 控制迴路所需要的。

十一、Gyro EXTI 的作用與對 Scheduler 的影響

11.1 EXTI 的物理作用

Gyro EXTI（External Interrupt）是陀螺儀晶片在新一批感測資料就緒時發出的硬體中斷訊號。對於 SPI 介面的陀螺儀（如 BMI270、ICM-42688-P），當內部 FIFO 或輸出暫存器有新樣本時，會透過 INT 引腳拉低觸發 MCU 的外部中斷。

11.2 EXTI ISR 做了什麼？極輕量的「時間戳記錄」

從 scheduler.c 的鎖相邏輯可以反推 ISR 的行為：

// ISR 中執行（極輕量） gyro->gyroSyncEXTI = getCycleCounter(); // 記錄中斷發生的精確 CPU 週期 gyro->detectedEXTI++; // 中斷計數器 +1

ISR 不會做以下事情：

  • ❌ 讀取 SPI 資料
  • ❌ 執行濾波運算
  • ❌ 執行 PID 運算
  • ❌ 呼叫任何任務函式

這與傳統設計「中斷來了就在 ISR 裡把事做完」截然不同。

11.3 會打斷 Scheduler 嗎？

技術上：會。 EXTI 是硬體中斷，優先級高於主迴圈，CPU 必然會跳轉到 ISR 向量表入口，執行完 ISR 後才返回 scheduler() 的輪詢等待迴圈。

實際影響：幾乎為零。 原因有三：

因素說明
ISR 極短僅 2~3 條指令（讀 cycle counter + 寫記憶體 + 遞增），耗時 < 1μs
無堆疊切換不觸發 PendSV，不進行任務排程，純粹的硬體中斷返回
不搶佔實時鏈真正的 Gyro/Filter/PID 執行是在主迴圈輪詢到精確時間點後才開始，而非中斷觸發

11.4 Scheduler 如何利用 EXTI 資訊？

EXTI 的時間戳被用於鎖相環 (PLL) 校正，而非直接觸發任務：

// scheduler.c 中的鎖相邏輯 int32_t gyroSkew = cmpTimeCycles(nextTargetCycles, gyro->gyroSyncEXTI) % desiredPeriodCycles; if (gyroSkew > (desiredPeriodCycles / 2)) { gyroSkew -= desiredPeriodCycles; // 處理環繞 } accGyroSkew += gyroSkew; // 每 GYRO_LOCK_COUNT 個週期校正一次 if (gyro->detectedEXTI >= terminalGyroLockCount) { lastTargetCycles -= (accGyroSkew / GYRO_LOCK_COUNT); // 消除累積漂移 }

這裡的設計精髓：

  • EXTI 提供「真實的物理時間基準」：陀螺儀晶片內部有自己的時脈，實際輸出速率與 MCU 的 desiredPeriodCycles 理論值存在微小漂移。
  • Scheduler 主動追蹤而非被動響應：Scheduler 透過比較「預期執行時刻 (nextTargetCycles)」與「實際 EXTI 時刻 (gyroSyncEXTI)」，緩慢調整 lastTargetCycles，讓軟體迴路與硬體陀螺儀「鎖相」。
  • 無累積誤差：若無此機制，125μs 的週期經過數千次後會產生明顯的相位漂移，導致控制迴路與感測資料不同步。

11.5 與傳統中斷驅動的對比

設計模式ISR 內容Scheduler 角色時序精度
傳統 ISR 驅動 讀取資料 + 濾波 + PID 僅執行背景任務 受中斷延遲抖動影響
Betaflight 模式 僅記錄時間戳 輪詢等待後執行完整鏈 次微秒級，無抖動
總結： Gyro EXTI 是「同步基準訊號」，而非「任務觸發訊號」。它會在硬體層短暫打斷 CPU（< 1μs），但 ISR 極輕量，不影響 Scheduler 的排程邏輯。Scheduler 利用 EXTI 的時間戳進行鎖相校正，確保軟體的 Gyro/Filter/PID 執行時刻與硬體感測器的實際輸出時刻長期同步。

十二、同步基準訊號與鎖相環 (PLL) 機制

12.1 為什麼需要參考訊號？

MCU 的 CPU 週期計數器 (DWT_CYCCNT) 與陀螺儀晶片內部的取樣時脈是兩個獨立的振盪源：

  • MCU 晶振：例如 168MHz，由外部石英振盪器驅動
  • Gyro 晶振：例如 32.768kHz 或內部 RC，用於決定實際的輸出速率

兩者之間存在：

  1. 頻率偏移（Frequency Offset）：標稱 8KHz 實際可能是 8003.2Hz
  2. 相位漂移（Phase Drift）：每次週期的微小誤差會隨時間累積

如果沒有 EXTI 提供「真實世界發生了什麼」的資訊，Scheduler 只能盲目相信 desiredPeriodCycles 這個理論值，最終導致：

  • 軟體以為該讀取新資料了，但硬體還沒準備好 → 讀到舊資料
  • 長期累積後，控制迴路與感測器輸出完全失步

12.2 Betaflight 的軟體 PLL 結構

從 scheduler.c 的鎖相邏輯可以對應到標準 PLL 的三個核心組件：

相位檢測器：gyroSkew = cmpTimeCycles(nextTargetCycles, gyro->gyroSyncEXTI) % desiredPeriodCycles • 環路濾波器：accGyroSkew += gyroSkew （積分器，平滑單一週期雜訊，保留長期漂移趨勢） • 數控振盪器：lastTargetCycles -= (accGyroSkew / GYRO_LOCK_COUNT) （根據累積誤差回授校正） 註：若軟體持續落後硬體，就把目標時刻往前拉；若超前，就往後推。

12.3 相位檢測器 (Phase Detector)

int32_t gyroSkew = cmpTimeCycles(nextTargetCycles, gyro->gyroSyncEXTI) % desiredPeriodCycles; if (gyroSkew > (desiredPeriodCycles / 2)) { gyroSkew -= desiredPeriodCycles; // 處理環繞（wrap-around） }

這行程式碼就是相位檢測器：它計算「軟體預計執行時刻」與「硬體實際就緒時刻」之間的時間差。

  • 若 gyroSkew > 0：表示軟體跑太慢（落後硬體）
  • 若 gyroSkew < 0：表示跑太快（超前硬體）

12.4 環路濾波器 (Loop Filter)

accGyroSkew += gyroSkew;

單一週期的 gyroSkew 可能因中斷延遲或雜訊而波動，因此需要累積（積分）來平滑。這相當於一個一階低通濾波器 / 積分器，濾除高頻抖動，只保留長期漂移趨勢。

每 GYRO_LOCK_COUNT 個週期才執行一次校正，進一步降低對單一週期雜訊的敏感度。

12.5 數控振盪器 (NCO - Numerically Controlled Oscillator)

if (gyro->detectedEXTI >= terminalGyroLockCount) { lastTargetCycles -= (accGyroSkew / GYRO_LOCK_COUNT); // 回授校正 accGyroSkew = 0; // 重置累積器 }

這是 PLL 的回授路徑：根據累積的相位誤差，調整下一次的目標時刻 lastTargetCycles。

  • 如果軟體持續落後硬體 → 把目標時刻往前拉
  • 如果軟體持續超前硬體 → 把目標時刻往後推

12.6 EXTI 的角色 = 參考時脈 (Reference Clock)

在標準 PLL 理論中，參考訊號必須具備以下特性，而 Gyro EXTI 恰好滿足：

PLL 對參考訊號的要求Gyro EXTI 的表現
穩定且已知頻率Gyro 輸出速率由晶片內部 PLL/DLL 鎖定，極穩定
與被控系統相關直接標記「新資料就緒」這個物理事件
低抖動 (Low Jitter)硬體中斷延遲 < 1μs，相對於 125μs 週期可忽略
持續可用只要 Gyro 運作，EXTI 持續以固定間隔產生
如果沒有 EXTI，Betaflight 的調度器就退化成「開環振盪器」——只根據 desiredPeriodCycles 這個理論值自嗨，無法感知也無法修正與真實世界的偏差。

12.7 但 EXTI 不是 PLL 的全部

同步基準訊號雖然是必要條件，但單有它還不夠：

缺少的組件後果
沒有相位檢測不知道軟體與硬體差了多少
沒有環路濾波單一週期的誤差可能是雜訊，不該立即反應
沒有回授調整知道了誤差卻不改，等於沒鎖相

Betaflight 的設計巧妙之處在於：它把完整的 PLL 邏輯全部壓縮在 Scheduler 主迴圈的幾行程式碼中，沒有額外的中斷、沒有專用的 PLL 硬體模組，純粹以軟體實現。

12.8 總結

Gyro EXTI 是鎖相環的「參考輸入端」，是 PLL 能夠閉環運作的必要前提，但並非 PLL 本身。

完整的鎖相環需要四個環節協同運作：

  1. 參考訊號（Gyro EXTI ← 這是硬體給的）
  2. 相位檢測（gyroSkew 計算 ← 軟體實現）
  3. 環路濾波（accGyroSkew 累積 ← 軟體實現）
  4. 回授調整（lastTargetCycles 修正 ← 軟體實現）
Betaflight 的創新不在於使用了 EXTI（很多飛控都接 Gyro INT），而在於它沒有讓 EXTI 直接觸發任務執行，而是讓 EXTI 作為 PLL 的參考輸入，由 Scheduler 主動輪詢並鎖相後，再在精確的本地時刻執行控制鏈。這種「軟 PLL + 輪詢同步」的組合，才是其硬實時精度的核心秘密。
