1. 完整控制架構與分項解說

系統總覽

Betaflight 是一套針對 FPV 競速無人機優化的開源飛行控制韌體，以 STM32F405（ARM Cortex-M4, 168MHz, 單精度 FPU, DSP 指令集）為核心，採用裸機（Bare-metal）架構——沒有 RTOS 的 context switch、tick 中斷延遲與記憶體保護 overhead。這個選擇本質上是一個確定性（Determinism）優先於抽象化的工程取捨：PID 迴路要求「取樣—運算—輸出」的延遲抖動（jitter）控制在個位數微秒等級，任何 RTOS 排程不確定性都會直接轉換成姿態控制誤差。相對地，代價是所有任務必須手動管理執行時間預算，且沒有記憶體保護，任一任務的 bug 都可能破壞全域狀態。

從控制理論角度看，整個系統可視為一個取樣資料系統（Sampled-data System）：感測器取樣頻率 $f_s$ 決定了控制迴路的 Nyquist 頻率上限（$f_s/2$），也決定了濾波器與 PID 微分項可用的頻寬。這是後續第 2、3 章時序與濾波器設計的理論基礎。

1.2 核心控制迴路

級聯控制架構 (Cascaded Control) ▼
// 外環：角度環 (Angle Loop) — 僅在自穩模式啟用 angle_error = desired_angle - measured_angle rate_setpoint = Kp_angle * angle_error // 內環：角速度環 (Rate Loop) — 核心控制迴路 rate_error = rate_setpoint - gyro_filtered P = Kp_rate * rate_error I += Ki_rate * rate_error * dt D = Kd_rate * (rate_error - prev_error) / dt // 輸出 = P + I + D + Feedforward motor_output = Mixer(throttle, roll_pid, pitch_pid, yaw_pid)

競速模式下通常直接使用 Rate Mode（僅內環），消除外環延遲，達到最高響應速度。

級聯設計的頻寬分離原則：外環（角度環）的頻寬必須顯著低於內環（角速度環），通常相差 5-10 倍以上，否則兩迴路會互相耦合產生振盪。這也是為何角度環常以較低頻率（甚至只需一個比例增益 $K_{p,angle}$，不含 I/D 項）運作即可——它只需提供內環的 setpoint，真正的擾動抑制仍由高頻的 rate loop 完成。此外，實際輸出還包含 PID Sum 限幅（iterm windup 保護）與抗飽和（anti-windup）機制，避免馬達達到最大出力時 I 項持續累積造成的過衝，此處程式碼為教學簡化版本，省略了這些保護邏輯。

2. 時序控制、任務排程與中斷機制

核心設計哲學

Betaflight 採用合作式排程（Cooperative Scheduling）結合靜態優先順位（Static Priority），無 RTOS，所有任務在單一執行緒中依優先順序執行，確保 PID 迴路的確定性延遲。嚴格來說這不是搶佔式（preemptive）排程——一個任務一旦開始執行就會跑到完成，排程器只在任務之間的邊界做選擇，因此「優先順序」實際上決定的是誰先被選中執行，而非執行中被中斷。這正是為何 2.3 節強調「ISR 極簡化」原則：真正能打斷主循環的只有硬體中斷，任務層級沒有搶佔能力。

防止任務餓死（Starvation）與動態優先權：單純的靜態優先順序排序有個陷阱——若高優先順位任務持續佔用 CPU，低優先順位任務可能永遠得不到執行機會。Betaflight 排程器透過 taskAgePeriods（任務自上次執行以來累積的「期望週期倍數」）做動態優先權放大：其公式為 dynamicPriority = 1 + staticPriority × taskAgePeriods。這意味著等待越久的任務，其有效優先權會隨靜態優先級「線性放大」，而非僅做固定加分。此外，排程器在接近陀螺儀中斷邊界時會進入 busy-poll 精準命中同步點（見 2.3.1 節），並透過 accGyroSkew 追蹤實際 EXTI 週期做時鐘鎖定校正——這是確保 PID 時序確定性的核心機制。

2.1 任務排程器架構

排程器位於 src/main/scheduler/scheduler.c，核心為一個按 staticPriority 排序的任務佇列。每個任務的執行週期由 desiredPeriodUs 定義，排程器計算 taskAgePeriods（距上次執行經過了多少個期望週期）來決定動態優先權：

typedef struct { taskFunc_t taskFunc; // 任務函數指標 uint32_t desiredPeriodUs; // 期望執行週期 (us) uint8_t staticPriority; // 靜態優先順序 (1-6) timeDelta_t taskAgePeriods; // 距上次執行的「期望週期倍數」 } cfTask_t;

動態優先權的計算公式為 dynamicPriority = 1 + staticPriority × taskAgePeriods。當多個任務同時就緒時，dynamicPriority 最高者獲得執行權；這讓中低優先順位的週期性任務（如電池監測、OSD）即使在高負載下也能保證最終被執行到，避免餓死。整個機制本質上是「軟即時（Soft Real-Time）」排程器：它不像 RTOS 提供數學上可證明的時限保證，而是依賴時間預算遠小於週期（1KHz 下僅用掉 ~8% CPU）來換取足夠的安全餘裕。

2.3.1 陀螺儀同步鎖定（Gyro Sync Lock）

為了讓排程器與陀螺儀硬體中斷（EXTI）保持長期同步，Betaflight 實作了週期鎖定（Gyro Lock）機制，這是課程舊版未涵蓋的關鍵細節：

  1. Skew 累積：每次陀螺儀 EXTI 觸發時，記錄 gyroSyncEXTI 時間戳。排程器比較「預期下次執行點 nextTargetCycles」與「實際 EXTI 時刻」的差值，累積到 accGyroSkew。
  2. 週期校正：每累積 GYRO_LOCK_COUNT 個週期後，將平均 skew accGyroSkew / GYRO_LOCK_COUNT 回饋到 lastTargetCycles，逐步消除漂移。
  3. Busy-Poll 命中：當排程器判斷距離下次 gyro 邊界小於 schedLoopStartCycles 時，會進入 while (schedLoopRemainingCycles > 0) 迴圈持續讀取 getCycleCounter()，直到硬體週期到達才執行 Gyro Task，確保 jitter 最小化。
// scheduler.c: 週期鎖定與 busy-poll 核心邏輯（簡化） // 1. 計算實際 gyro 週期並更新 desiredPeriodCycles if (gyro->detectedEXTI >= terminalGyroRateCount) { desiredPeriodCycles = sampleCycles / GYRO_RATE_COUNT; } // 2. 累積 skew（預期時刻與實際 EXTI 的相位差） int32_t gyroSkew = cmpTimeCycles(nextTargetCycles, gyro->gyroSyncEXTI) % desiredPeriodCycles; if (gyroSkew > (desiredPeriodCycles / 2)) gyroSkew -= desiredPeriodCycles; accGyroSkew += gyroSkew; // 3. 每 GYRO_LOCK_COUNT 週期校正一次目標時刻 if (gyro->detectedEXTI >= terminalGyroLockCount) { lastTargetCycles -= (accGyroSkew / GYRO_LOCK_COUNT); accGyroSkew = 0; } // 4. 接近邊界時 busy-poll 等待，精準命中 while (schedLoopRemainingCycles > 0) { nowCycles = getCycleCounter(); schedLoopRemainingCycles = cmpTimeCycles(nextTargetCycles, nowCycles); }

3. 感測器融合與濾波器設計

本章討論的濾波與融合演算法都是在解一個共同的問題：陀螺儀原始訊號中同時混有「真實姿態變化」與「機械振動噪聲」，兩者在時域上難以分離，但在頻域上通常可分離（真實控制動作多在數十 Hz 以下，槳葉/馬達共振多在 100Hz 以上）。因此濾波器鏈的設計本質上是在相位延遲（會直接劣化 PID 的相位裕度、增加震盪風險）與噪聲抑制之間取捨——這條主線貫穿 3.3 至 3.5 節。

陀螺儀採用「中斷驅動 + DMA」混合模式：

  1. 陀螺儀 INT 引腳產生中斷（數據就緒通知）
  2. EXTI ISR 中啟動 SPI DMA 傳輸（14 bytes 讀取）
  3. DMA 完成中斷觸發數據處理（濾波器鏈）
  4. 處理後數據存入全域緩衝區，供 PID 任務使用

為何不用輪詢（Polling）？若改為在主循環中固定週期讀取陀螺儀，取樣時刻會與感測器實際完成轉換的時刻不同步，引入額外的取樣抖動（sampling jitter），且無法保證讀到的是「最新」數據。中斷驅動模式讓取樣時刻直接鎖定在感測器 ODR（Output Data Rate）邊界上，這是達成 <100us 級延遲確定性的關鍵。

3.3.2 Notch Filter (陷波濾波器)

Notch Filter 用於精確抑制特定頻率的機械共振（如槳葉轉速頻率及其諧波），是 IIR Biquad 的高 Q 值應用：

// Notch Filter 參數計算 // centerFreq: 中心頻率 (Hz) // cutoff: 帶寬 (Hz) — Q = centerFreq / cutoff void biquadFilterUpdateNotch( biquadFilter_t *filter, float centerFreq, float cutoff, float sampleRate ) { const float omega = 2.0f * M_PIf * centerFreq / sampleRate; const float sn = sinf(omega); const float cs = cosf(omega); // 注意：頻寬轉 alpha 需用 sinh (雙曲正弦)，非 sinf； // 這是標準 RBJ Audio-EQ-Cookbook 的 bandwidth 定義。 const float alpha = sn * sinhf(M_LN2f / 2.0f * cutoff / centerFreq * omega / sn); filter->b0 = 1.0f + alpha; filter->b1 = -2.0f * cs; filter->b2 = 1.0f - alpha; filter->a0 = 1.0f + alpha; filter->a1 = -2.0f * cs; filter->a2 = 1.0f - alpha; // 正規化：實際套用前，b0/b1/b2/a1/a2 均需除以 a0 (=1+alpha) // 使 filter->a0 恆為 1，這樣 biquadFilterApply() 才能省略 /a0 運算 }

參數物理意義：$Q = f_{center}/BW$ 決定陷波的「窄」與「深」——Q 越高，凹陷範圍越窄，越不會誤傷相鄰的有用訊號（如控制指令本身的低頻成分），但對中心頻率的估計精度要求也越高。這正是為何靜態 Notch（手動設定固定頻率）在槳葉轉速變化時效果會變差：轉速一旦偏離設定頻率，陷波位置就跟著失準，這也是下方 Dynamic Notch 存在的動機。

Dynamic Notch Filter (動態陷波)

Betaflight 4.x 引入基於 FFT 的動態 Notch，對陀螺儀取樣做滑動視窗 FFT（通常搭配 Hann window 降低頻譜洩漏），找出頻譜中的峰值頻率（通常是馬達/槳葉共振及其諧波），即時調整 1-3 組 Notch 的中心頻率使其持續對準。需要較高 CPU 負載（FFT 運算 + 峰值追蹤演算法），建議在 4KHz 以下迴路使用；8KHz 以上通常改用 3.5 節的 RPM-based Notch，因為它不需要 FFT，CPU 成本幾乎與轉速無關。4.3 版新增 Multi Dynamic Notch，可同時追蹤多個獨立峰值而非單一峰值，對多槳/多諧振源的機架效果更好（見 4.3 Tuning Notes）。

3.4 感測器融合：Mahony AHRS 四元數互補濾波器

Betaflight 使用「Mahony AHRS」而非簡單的 Euler 角加權平均

課程舊版將互補濾波器描述為「兩個 Euler 角度直接加權平均」，這是取樣資料系統教學中常見的簡化模型，但與 Betaflight 實作有本質差異。實際上 Betaflight 採用的是 Mahony AHRS（Nonlinear Complementary Filter on SO(3)）：以四元數 q 維持姿態，透過 PI 回授控制器修正角速度，再對四元數做運動學積分。這是一個在旋轉群 SO(3) 上運作的非線性濾波器，具備全局收斂性，不會因大角度而出現 Euler 奇異點問題。

從數學結構看，這與 CURIO4 韌體中使用的 Mahony Quaternion AHRS + SO(3) vee-map error 架構屬於同一族工具：誤差向量並非在 Euler 空間做線性相減，而是透過外積（cross product）從旋轉矩陣的估計重力列與加速度計量測值之間提取 SO(3) 上的切空間誤差（即 vee-map 的離散實現），再注入角速度做 PI 補償。

// imu.c: imuMahonyAHRSupdate — PI 回授 + 四元數積分 // 1. 初始化誤差向量（body frame） float ex = 0, ey = 0, ez = 0; // 2a. 航向誤差（Mag / GPS COG）經 earth-Up 列轉入 body frame // rMat.m[NWU_U][*] 是 earth-Up 在 body frame 的投影（即估計重力方向） ex += rMat.m[NWU_U][X] * (headingErrCog + headingErrMag); ey += rMat.m[NWU_U][Y] * (headingErrCog + headingErrMag); ez += rMat.m[NWU_U][Z] * (headingErrCog + headingErrMag); // 2b. 加速度計誤差：估計重力方向與量測方向的外積 if (useAcc && recipAccNorm > 0.01f) { // cross(estimated_gravity, measured_accel) ex += (ay * rMat.m[NWU_U][Z] - az * rMat.m[NWU_U][Y]); ey += (az * rMat.m[NWU_U][X] - ax * rMat.m[NWU_U][Z]); ez += (ax * rMat.m[NWU_U][Y] - ay * rMat.m[NWU_U][X]); } // 3. 為何不用 EKF？
EKF 需要維護狀態協方差矩陣（12×12 或更大），每次更新需數百次浮點運算。Mahony AHRS 僅需一次 PI 回授與四元數積分，計算量為 EKF 的 1/50 以下，延遲極低。更重要的是，Mahony 直接在 SO(3) 上運作，不受 Euler 角萬向節鎖死（gimbal lock）影響，對於 FPV 競速機的短時間高動態飛行已足夠精確。
增益調度與收斂策略：imuCalcKpGain ▼

為了加速起飛前的初始收斂與墜機後的快速復位，imu.c 實作了動態的 dcmKpGain 調度器（imuCalcKpGain）：

  • 飛行中（Armed）：使用預設 imuDcmKp（約 0.25），避免高增益放大振動雜訊。
  • 解鎖後靜止（Disarmed Quiet）：若陀螺儀活動低於 15°/s 達 250ms，進入 500ms 的高增益窗口，dcmKpGain = imuDcmKp × 100，讓姿態快速收斂。
  • 一般待機（Disarmed）：使用 imuDcmKp × 10，維持比飛行時更快的追蹤速度。

這種狀態機式的增益排程確保了「地面靜止時快速對齊」與「空中飛行時低雜訊」兩個矛盾的目標同時達成。

4. ExpressLRS (ELRS) 遙控接收機

ELRS 概述

ExpressLRS (ELRS) 是開源的 2.4GHz / 900MHz 遙控協議，以極低延遲、高刷新率、長距離為設計目標，已成為 FPV 領域的主流標準。

與傳統 PWM/PPM 或早期 2.4GHz 協議（如 FrSky ACCST）相比，ELRS 的關鍵創新在於採用 LoRa 展頻調變（Chirp Spread Spectrum 的變體）搭配動態封包率（Adaptive Packet Rate）：訊號良好時使用高封包率換取低延遲，訊號衰弱時自動降頻換取更長的展頻增益（Processing Gain），以延伸有效距離——這是一種即時的延遲/距離動態取捨，而非固定規格。

UART 接收使用 DMA + 空閒中斷（Idle Interrupt）模式：DMA 持續接收數據到緩衝區，當 UART 檢測到總線空閒（超過 1 字符時間無數據）時觸發中斷，標記一幀數據接收完成。這個設計避開了「逐 byte 中斷」的高 CPU 開銷（420000 baud 下每秒可達數萬次中斷），是 2.3 節「DMA 優先」原則在 RC 輸入路徑上的具體實現。

5. DShot600 數位 ESC 協議

DShot 概述

DShot (Digital Shot) 是專為無人機設計的數位 ESC 通訊協議，取代傳統類比 PWM（1000-2000us 脈衝寬度調變），以數位編碼傳輸油門指令，具備校驗和、雙向通訊等特性。

傳統類比 PWM 的根本限制在於：油門值以「脈衝寬度」編碼，ESC 端需靠計時器測量高電平持續時間，容易受電磁雜訊與時鐘誤差影響，且無法傳遞校驗資訊——ESC 完全無法分辨收到的是有效指令還是雜訊干擾。DShot 把類比問題轉換成數位問題：只要 ESC 能正確判斷「高電平時間佔整個 bit 週期的比例是否超過門檻」，就能可靠解碼，且每個封包都帶 CRC，錯誤封包會被直接捨棄而非誤執行，這是数位協議相較類比協議在可靠性（Reliability）上的本質優勢。

5.3 位元編碼方式

DShot 使用 不歸零反相編碼（NRZ, Non-Return-to-Zero），每個 bit 以高低電平時間比例區分 0 與 1：

Bit "0": T0H = 625ns (高) + T0L = 1040ns (低) = 1.67us total
Bit "1": T1H = 1250ns (高) + T1L = 420ns (低) = 1.67us total

無論 0 或 1，總週期固定為 1.67us（@ 600Kbps），ESC 通過測量高電平持續時間來判斷 bit 值。這種設計對時鐘漂移具有較好的容忍度：由於判斷依據是「高電平佔週期的比例」而非絕對時間，只要 ESC 與 FC 的時鐘誤差在合理範圍內（通常 <5%），37.5% 與 75% 這兩個門檻仍有足夠的判別餘裕（decision margin），不需要像 UART 那樣要求雙方時鐘高度一致。

5.4 Betaflight 中的 DShot 實現

DShot 輸出驅動架構 ▼
// DShot600 封包編碼 (16 bits -> 16 x 1.67us = 26.7us) uint16_t prepareDshotPacket(uint16_t value, bool requestTelemetry) { uint16_t packet = (value << 1) | (requestTelemetry ? 1 : 0); uint8_t crc = (~(packet ^ (packet >> 4) ^ (packet >> 8))) & 0x0F; packet = (packet << 4) | crc; return packet; // 16-bit DShot frame } // DMA 傳輸：將 16-bit 封包轉換為 GPIO 位元流 // 每個 bit 佔用 1 byte DMA buffer (bit-bang via timer) void pwmWriteDshotInt(uint8_t index, uint16_t value) { uint16_t packet = prepareDshotPacket(value, false); for (int i = 0; i < 16; i++) { if (packet & 0x8000) { // Bit "1": 高電平 75% 時間 dmaBuffer[i] = MOTOR_BIT_1; } else { // Bit "0": 高電平 37.5% 時間 dmaBuffer[i] = MOTOR_BIT_0; } packet <<= 1; } // 啟動 DMA 傳輸到 GPIO DMA_SetCurrDataCounter(dmaChannel, 16); DMA_Cmd(dmaChannel, ENABLE); }

DShot 輸出使用 Timer + DMA + GPIO 組合：Timer 產生固定頻率的更新事件，DMA 將預先計算好的位元流從記憶體搬移到 GPIO 輸出寄存器，無需 CPU 介入每個 bit 的切換。這實際上是把 GPIO 訊號生成問題「偽裝成」PWM 輸出問題——透過將 Timer 的 Compare 暫存器值逐一由 DMA 更新，讓每次 PWM 週期產生不同占空比，達成任意位元流的輸出。這種技巧（有時稱為 DMA-driven bit-banging）讓 STM32 不需要專用的序列埠硬體就能產生自訂協議波形，是嵌入式系統中常見的通用手法。

CRC 計算補充：上方 prepareDshotPacket() 對所有封包一律做 CRC 反相（~(...)），但嚴格來說標準 DShot（單向）使用未反相的 CRC，僅雙向 DShot（Bidirectional DShot，5.5 節）因為訊號極性反轉的緣故才對 CRC 做反相處理，藉此讓 ESC 端能分辨這是雙向模式的封包。此處為簡化教學範例，實作時需依協議版本正確切換。

6. 飛行模式 (Flight Modes)

飛行模式概述

Betaflight 提供多種飛行模式，通過 AUX 通道（通常是 CH5-CH8）切換。不同模式改變 PID 控制架構、感測器使用方式與安全行為。

從控制系統的角度看，這些模式並非各自獨立的演算法，而是共用同一組 rate-loop PID 核心，在其外層疊加不同的 setpoint 產生策略與增益調整規則——理解這點後，6.1 的每個模式都可以歸類為「setpoint 怎麼來」（ACRO/ANGLE/HORIZON/HEADFREE/GPS RESCUE）或「增益怎麼變」（AIR MODE、6.3 的 Gain Scheduling）兩類問題，而非需要死記硬背的獨立行為清單。

6.1 主要飛行模式

ACRO / RATE Mode

純角速度控制，無自穩。搖桿直接對應角速度設定點。

控制架構：僅內環（Rate Loop）
陀螺儀：必需
加速度計：不使用
用途：競速、花飛、專業飛手首選
延遲：最低（無外環計算）
上手難度：高 — 需手動修正姿態

ANGLE Mode (自穩)

搖桿對應目標角度，飛控自動維持水平。外環 + 內環級聯控制。

控制架構：外環（Angle Loop）+ 內環（Rate Loop）
陀螺儀：必需
加速度計：必需（提供重力基準）
用途：初學者、航拍、懸停
延遲：較高（外環計算 + 加速度計融合）
上手難度：低 — 鬆手自動回平

HORIZON Mode

ANGLE 與 ACRO 的混合模式。小幅度打桿時自穩，大幅度時進入 Rate 模式。

控制架構：動態切換外環增益
切換條件：搖桿偏離中點 > 80% 時進入 ACRO
用途：初學者過渡、練習翻滾
特性：兼具自穩安全性與 ACRO 操控自由度

AIR MODE

非獨立模式，而是叠加於 ACRO/ANGLE 之上的功能。零油門時仍保持 PID 控制。

功能：油門為 0 時，I-term 與 P-term 仍作用
效果：執行翻滾/俯衝時，即使油門歸零也能維持姿態
用途：花式飛行必備（翻滾、倒飛、自旋）
注意：降落時需手動關閉，否則馬達不會完全停止

GPS RESCUE (返航)

失控時自動返航至起飛點。需配備 GPS 模組。

觸發條件：遙控器訊號遺失（Failsafe）
行為：爬升至設定高度 -> 直線飛回起飛點 -> 降落
控制：獨立導航 PID（位置環 + 速度環 + 姿態環）
限制：無避障能力，僅適用於開闊區域

HEADFREE (無頭模式)

飛行方向與起飛時的機頭方向綁定，不受機身旋轉影響。

原理：將遙控器輸入從機體座標系轉換至地面座標系
用途：初學者、方向感迷失時的輔助
限制：YAW 旋轉時可能產生座標轉換誤差

6.2 模式切換機制

飛行模式通過 AUX 通道（CH5-CH8）的 PWM 值切換。Betaflight Configurator 中可設定每個模式的啟動閾值：

// 模式檢測邏輯 (簡化) if (rcData[AUX1] > 1700) { // AUX1 > 1700us -> 啟用 ANGLE Mode ENABLE_FLIGHT_MODE(ANGLE_MODE); } else if (rcData[AUX1] > 1300) { // AUX1 1300-1700us -> HORIZON Mode ENABLE_FLIGHT_MODE(HORIZON_MODE); } else { // AUX1 < 1300us -> ACRO Mode (預設) DISABLE_FLIGHT_MODE(ANGLE_MODE | HORIZON_MODE); }

模式切換在 PID 迴路之外執行，不影響控制時序。切換時可能產生短暫的設定點跳變，需通過 RC Smoothing 緩和。

TPA（Throttle PID Attenuation）的物理成因：馬達推力與轉速並非線性關係（推力 $\propto \omega^2$），且高油門時電池壓降增加、馬達接近飽和轉速，使得相同的 PID 輸出在高油門區間造成的角加速度變化率遠大於低油門區間——換言之，系統的有效增益隨油門上升而增加。若不做補償，高速飛行時同樣的 PID 增益極易在高油門下產生震盪。TPA 用近似線性的方式反向衰減 P/D 增益，本質上是一種簡化版的增益排程（Gain Scheduling）補償非線性受控體的做法，數學上可表示為 $K_{eff} = K_{base} \times [1 - TPA\_rate \times \max(0, throttle - TPA\_breakpoint)]$。

Anti-Gravity 的成因：油門突然拉高時，機身因慣性略微下沉（姿態角瞬間偏離 setpoint），此誤差本應由 I 項累積修正，但正常的 I 項時間常數對於這種瞬態往往「反應太慢」；Anti-Gravity 偵測到油門變化率超過閾值時，短暫放大 I 項增益，讓積分器能更快地追上這個瞬態誤差，避免每次拉油門都出現肉眼可見的「點頭」現象。

7. 安全機制 (Safety Systems)

安全設計哲學

Betaflight 的安全機制以「預防為主、分層保護」為原則，從上電到飛行結束，每個階段都有對應的保護措施。對於高速旋轉的槳葉（可達 300+ km/h 葉尖速度），任何疏忽都可能造成嚴重傷害。

這種分層設計可理解為縱深防禦（Defense in Depth）：任一單一機制失效（例如飛手忘記檢查螺旋槳方向、或 GPS 定位失準），系統仍應有其他獨立機制攔截風險（如解鎖前的姿態檢查、Failsafe 的 Drop Mode 保底）。7.1-7.4 節討論韌體層面的自動保護，7.5-7.6 節討論操作與法規層面的人為程序——兩者互補，缺一不可，因為韌體無法防範操作疏失（如飛錯方向），人為檢查也無法在毫秒級的訊號中斷中即時反應。

8. 任務調度與優先級設計 (Task Scheduling)

任務調度總覽

Betaflight 採用協作式優先級搶佔排程器（Priority-based Cooperative Scheduler），所有任務以 task_t 結構描述，並在編譯期透過 DEFINE_TASK 宏靜態配置。排程器根據「靜態優先級 + 動態時限」決定執行順序，確保陀螺儀→濾波→PID這條控制迴路始終獲得最高優先級，同時讓非關鍵任務（如 OSD、LED）在剩餘 CPU 週期中執行。

從 tasks.c 的設計可觀察到一個核心原則：「週期與優先級脫鉤」。高頻任務不一定高優先級（如 1 kHz 的 MAIN 僅為 MEDIUM_HIGH），而低頻的 GYRO/PID 卻是 REALTIME——這反映了控制理論中「取樣頻率」與「控制延遲」的不同需求。

DEFINE_TASK 宏與任務屬性

每個任務透過以下宏定義六項屬性：

#define DEFINE_TASK(taskNameParam, subTaskNameParam, checkFuncParam, taskFuncParam, desiredPeriodParam, staticPriorityParam) { .taskName = taskNameParam, .subTaskName = subTaskNameParam, .checkFunc = checkFuncParam, .taskFunc = taskFuncParam, .desiredPeriodUs = desiredPeriodParam, .staticPriority = staticPriorityParam }
屬性說明範例
taskName任務主名稱，用於除錯與 CLI 顯示"GYRO", "PID", "RX"
subTaskName子任務名稱，區分同一任務內的不同階段"LOAD" (SYSTEM), "UPDATE" (MAIN)
checkFunc執行前檢查函數，回傳 true 才執行 taskFuncrxUpdateCheck, osdUpdateCheck
taskFunc實際執行的函數指標taskGyroSample, taskMainPidLoop
desiredPeriodUs期望執行週期（微秒），可動態重設TASK_PERIOD_HZ(1000) = 1000 µs
staticPriority靜態優先級，決定搶佔順序TASK_PRIORITY_REALTIME ~ LOWEST

六級優先級架構

優先級以枚舉定義，數值越小優先級越高。排程器在每次主迴圈結束時，從最高優先級開始遍歷，選擇「已逾時」且「檢查通過」的任務執行。

🔴 TASK_PRIORITY_REALTIME

最高優先級，控制迴路專用。任何情況下不可被搶佔延遲。

  • GYRO — 陀螺儀取樣（taskGyroSample）
  • FILTER — 濾波處理（taskFiltering）
  • PID — PID 控制運算（taskMainPidLoop）

週期通常為 TASK_GYROPID_DESIRED_PERIOD（如 125 µs @ 8 kHz）。這三個任務構成飛行控制的最小閉環，延遲抖動（jitter）必須控制在個位數微秒。

🟠 TASK_PRIORITY_HIGH

關鍵輸入與事件分發，直接影響飛行指令與系統反應。

  • RX — 接收機訊號處理（33 Hz 週期，含狀態機）
  • DISPATCH — 事件分派（1000 Hz）

RX 任務使用三狀態機（CHECK → MODES → UPDATE），並透過 schedulerIgnoreTaskExecRate() 與 schedulerSetNextStateTime() 實現動態執行時間預估。

🟡 TASK_PRIORITY_MEDIUM_HIGH

系統核心與背景維護，需穩定執行但可容忍少量延遲。

  • SYSTEM (LOAD) — 系統負載統計（10 Hz）
  • MAIN (UPDATE) — 主更新迴圈（1000 Hz），負責 SD 卡、Flash 等

🟢 TASK_PRIORITY_MEDIUM

感測器融合、導航與電池管理，對飛行安全有間接影響。

  • ACC — 加速度計（1000 Hz）
  • ATTITUDE — 姿態解算（100 Hz）
  • GPS / GPS_RESCUE — 定位與救援邏輯
  • BATTERY_VOLTAGE / CURRENT / ALERTS — 電池監控（5–50 Hz）
  • ESC_SENSOR — 電調回傳數據（100 Hz）
  • RCDEVICE / GIMBAL — 外接設備與雲台（20–100 Hz）

🔵 TASK_PRIORITY_LOW

人機介面、通訊與輔助飛行功能，可容忍較大延遲。

  • SERIAL — 串口通訊（100 Hz），註解明確指出「115200 baud 下 100 Hz 足夠清空 115 bytes」
  • OSD / TELEMETRY / LEDSTRIP — 圖傳疊加、遙測、燈帶
  • BARO / COMPASS / ALTITUDE — 氣壓計、羅盤、高度融合
  • ALTHOLD / POSHOLD — 定高與定點保持
  • BEEPER / CAMCTRL / CMS — 蜂鳴器、相機控制、CMS 選單
  • SPEED_NEGOTIATION / RC_STATS / OSD_CUSTOM_TEXT / DRONECAN

⚪ TASK_PRIORITY_LOWEST

診斷、監控與極低頻背景任務，僅在 CPU 空閒時執行。

  • STACK_CHECK — 堆疊使用量檢查（10 Hz）
  • VTXCTRL — 圖傳頻道/功率控制（5 Hz）
  • ADC_INTERNAL — 內部 ADC（1 Hz，通常用於溫度）
  • PINIOBOX / RANGEFINDER / OPTICALFLOW — IO 擴展、測距、光流
  • BST_MASTER_PROCESS — BST 匯流排處理（50 Hz）

任務啟用與動態週期調整

在 tasksInit() 中，系統根據硬體配置與使用者設定決定哪些任務被啟用，並可動態調整週期：

// 依據陀螺儀實際取樣時間設定控制迴路週期 rescheduleTask(TASK_GYRO, gyro.sampleLooptime); rescheduleTask(TASK_FILTER, gyro.targetLooptime); rescheduleTask(TASK_PID, gyro.targetLooptime); // 依據電池配置啟用電壓/電流任務 const bool useBatteryVoltage = batteryConfig()->voltageMeterSource != VOLTAGE_METER_NONE; setTaskEnabled(TASK_BATTERY_VOLTAGE, useBatteryVoltage); // 若啟用電壓跌落補償，提升電壓取樣率 if (isSagCompensationConfigured()) { rescheduleTask(TASK_BATTERY_VOLTAGE, TASK_PERIOD_HZ(FAST_VOLTAGE_TASK_FREQ_HZ)); } // 遙測協議差異化排程 if (rxRuntimeState.serialrxProvider == SERIALRX_CRSF) { rescheduleTask(TASK_TELEMETRY, TASK_PERIOD_HZ(500)); // CRSF 需要 2 ms 週期 }

這種設計體現了「條件編譯 + 執行期配置」的雙層彈性：#ifdef USE_GPS 等編譯開關決定程式碼是否編入，而 featureIsEnabled(FEATURE_GPS) 則在執行期決定是否排程，避免無謂的上下文切換。

RX 任務的狀態機與執行時間預估

taskUpdateRxMain() 是少數使用顯式狀態機的任務，因為其執行時間具有高度變異性（接收機封包到達為非週期事件）：

typedef enum { RX_STATE_CHECK, // 檢查是否有新封包 RX_STATE_MODES, // 處理飛行模式開關 RX_STATE_UPDATE, // 更新 rcCommand 與武裝狀態 RX_STATE_COUNT } rxState_e;

排程器透過 schedulerIgnoreTaskExecRate() 與 schedulerSetNextStateTime() 配合，讓 RX 任務在非 UPDATE 狀態時「不計入執行頻率」，僅依據預估的單狀態執行時間決定下次喚醒點。這種機制避免了傳統週期性輪詢造成的 CPU 浪費，同時確保封包到達時能及時處理。

任務統計與除錯

透過 TASK_SYSTEM 的 LOAD 子任務，Betaflight 持續追蹤每個任務的：

  • 平均執行時間（average execution time）：用於預估下次排程
  • 最大執行時間（max execution time）：檢測異常峰值
  • 延遲（lateness）：實際執行時間與期望週期的偏差
  • 負載百分比（load %）：該任務佔用的 CPU 比例

在 CLI 輸入 tasks 可查看即時統計；debug_mode = DEBUG_RX_STATE_TIME 則可觀察 RX 任務各狀態的執行時間分佈。這些數據對於調校「PID 迴路頻率 vs. 其他任務負載」的權衡至關重要。
